# 2026-07-11

今日周六，没有安排讲座和co-learning～那就随手记录一点今天对区块链的一些新了解。

今天了解了一下账户抽象和 ERC-4337。以前我对钱包的理解比较简单，觉得它就是用私钥控制地址，再通过签名发送交易。学完之后才发现，钱包也可以是一个带有验证逻辑的智能合约。

我重点看了 `UserOperation`、`Bundler`、`EntryPoint` 和 `Paymaster` 的作用。用户提交的并不是普通交易，而是一条操作意图；Bundler 负责收集并提交，EntryPoint 负责验证和执行。如果项目接入 Paymaster，还可以替用户支付 Gas。这样一来，新用户不必刚进入应用就先购买原生代币，使用过程会顺畅很多。

账户抽象最吸引我的地方，是钱包的权限规则可以自行设计。例如设置每日转账限额、多人共同确认大额交易，或者通过其他设备和联系人恢复账户。这让我意识到，钱包不一定只是一个存放资产的地址，它也可以承担账户管理和安全控制的功能。

目前我对底层验证过程还不算熟悉，尤其是 Bundler 如何筛选操作、Paymaster 怎样避免被滥用。下一步可以找一个支持 ERC-4337 的测试网钱包实际操作，再结合区块浏览器观察一笔 `UserOperation` 最后是怎样上链的。

\## Agent Bounty Escrow Demo  
  
今天重点推进的是 \`Agent 任务托管\` 这个 demo。这个项目的想法是：用户发布一个小任务，并把 MON 赏金锁定到智能合约里；执行者接单、提交结果后，发布者确认完成，合约自动把赏金释放给执行者。  
  
我把它理解成一个适合 AI Agent 场景的小额任务托管产品。第一版可以先服务人类执行者，后面再扩展到 AI Agent 自动接单、提交结果和收款。  
  
今天整理出来的核心流程是：  
  
\`\`\`text  
发布任务 -> 锁定赏金 -> 接单 -> 提交结果 -> 确认完成 -> 释放付款  
\`\`\`  
  
已经完成的 demo 内容包括：  
  
\- 写了 Solidity 赏金托管合约 \`AgentBountyEscrow\`。  
\- 设计了任务状态：Open、Accepted、Submitted、Approved、Cancelled、Refunded。  
\- 支持发布任务并锁定赏金。  
\- 支持执行者接单。  
\- 支持执行者提交结果链接或说明。  
\- 支持发布者确认完成并释放赏金。  
\- 支持取消任务和超时退款的基础逻辑。  
\- 用 React + ethers.js 做了一个毛坯前端。  
\- 前端支持连接 MetaMask。  
\- 支持 Monad Testnet 网络识别和切换提示。  
\- 没有合约地址时可以使用演示模式先跑流程。  
\- 配置了 GitHub Pages 部署相关内容。

\### Monad 高频场景作业  
  
我还整理了一个 Tech 方向的高频交互场景：\`Monad Study Quest\`。  
  
这个想法面向训练营或学习社区，场景包括：  
  
\- 每日打卡。

我在这个作业里重点思考了一个问题：什么内容适合上链，什么内容不需要上链。

\## 今天学习到的内容  
  
\### 1. DApp 的完整结构  
  
之前我对 DApp 的理解比较碎片化，今天通过 demo 更清楚地看到它至少包含几层：  
  
\- 合约层：定义资产托管、任务状态和结算规则。  
\- 钱包层：用户用钱包地址作为身份，并用签名确认操作。  
\- 前端层：展示任务、按钮、状态和交易反馈。  
\- 网络层：需要确认当前是否在 Monad Testnet。  
\- 验证层：通过区块浏览器查询交易和合约状态。  
  
\### 2. 为什么这个 demo 需要上链  
  
如果只是普通任务列表，其实数据库就够了。但 \`Agent Bounty Escrow\` 需要上链的原因在于：  
  
\- 赏金托管需要公开可信。  
\- 任务状态变化需要可验证。  
\- 放款规则需要由合约执行。  
\- 钱包地址可以积累任务历史和信誉。  
\- 未来 AI Agent 可以直接用钱包参与任务和收款。  
  
这也是我今天对 Web3 产品更深的一点理解：不是所有功能都应该上链，只有那些需要可信结算、公开验证、资产流转或身份信誉沉淀的部分，才更适合上链。  
  
\### 3. Agent 支付方向  
  
晚上读了 7 月 8 日的 AI Agent 支付分享纪要，里面对我启发比较大的是：Agent 如果要真正执行任务，就不可避免会涉及支付。  
  
会议里提到的重点包括：  
  
\- Agent 支付目前更适合从小额微支付开始。  
\- 用户可以先授权预算，Agent 在预算范围内执行支付。  
\- 一次性 Agent Card 可以降低 Agent 乱花钱的风险。  
\- X402 这类协议可以让 Agent 直接调用付费 API。  
\- Agent 支付最核心的问题不是按钮怎么做，而是安全、风控、授权和约束。  
\- 当前阶段 Base + USDC 是比较现实的支付路径，但不同场景未来可能会适配不同链。  
  
这和我做的 \`Agent 任务托管\` demo 有一定关联。我的 demo 更偏任务赏金托管，分享会讲的是更大的 Agent 支付生态。它们共同指向一个方向：未来 Agent 不只是聊天或生成内容，而是可以完成任务、调用服务、产生收入和付款。  
  
\### 4. AI 写代码可以提速，但安全判断不能外包  
  
今天继续体会到，AI 很适合帮我搭项目骨架、解释报错、整理 README、生成前端和合约的基础版本。但涉及链上资产、合约权限、退款、放款、重入保护、私钥安全时，最后必须自己检查。  
  
尤其是合约类项目，不能因为代码能跑就认为安全。至少要检查：  
  
\- 谁能调用这个函数。  
\- 钱会不会被锁死。  
\- 退款和放款有没有重复转账风险。  
\- 状态是不是先更新再转账。  
\- 有没有把私钥、助记词、\`.env\` 提交到 GitHub。  
  
\## 今天遇到的问题  
  
1\. 一开始会把“能跑的前端 demo”和“真的链上 DApp”混在一起。后来理解到，演示模式只是帮助先体验流程，真正链上版本还需要部署合约、配置合约地址、连接正确网络并发起交易。  
2\. GitHub Pages 部署时需要注意 Vite 的 \`base\` 配置和环境变量配置，否则页面可能能打开但资源路径或合约地址不对。  
3\. 对任务数据放链上还是放链下还需要继续判断。第一版为了简单可以把简短说明写入链上，但后续长文本、附件、Agent 输出更适合放 IPFS、URL 或 hash。  
4\. 当前合约还没有争议处理机制。如果执行者提交了错误结果，第一版只能由发布者决定是否确认，后续可能需要仲裁、多签或评价机制。

## 1. DeFi 借贷协议的资金结构

DeFi 借贷通常采用资金池模式。存款人将资产存入协议形成流动性池，借款人抵押其他资产后，从池中借出所需资产。

存款人的收益主要来自借款人支付的利息。协议通常会从利息中提取一部分作为储备金，用来承担系统风险或补偿潜在损失。

借款流程可以概括为：

1. 用户存入 ETH、WBTC 等资产作为抵押品；
2. 协议通过预言机读取抵押资产的市场价格；
3. 根据抵押率和资产风险参数计算可借额度；
4. 用户借出 USDC、DAI 等资产；
5. 当抵押品价值下降到危险水平时，协议触发清算。

## 2. 利率模型

DeFi 借贷利率通常不是固定的，而是根据资金池利用率动态变化。

资金利用率可以简化表示为：

$
U = \frac{总借款金额}{资金池总流动性}
$

当利用率较低时，说明池中资金充足，借款利率相对较低；当利用率持续上升时，可供用户提取的资金减少，协议会提高借款利率。

提高利率主要有两个作用：

* 鼓励借款人尽快还款；
* 吸引更多存款人向资金池提供流动性。

很多协议采用分段利率曲线。当利用率超过某个最优值后，借款利率会快速上升，以避免资金池因流动性不足而无法满足用户提款需求。

## 3. 抵押率与健康因子

借贷协议通常要求超额抵押。例如，用户抵押价值 1,000 USDC 的 ETH，并不能直接借出等值资产，只能借出其中一部分。

健康因子可以简化理解为：

$
健康因子 =
\frac{抵押品价值 \times 清算阈值}{借款价值}
$

* **健康因子大于 1**：仓位暂时安全；
* **健康因子接近 1**：仓位存在清算风险；
* **健康因子小于 1**：清算人可以参与清算。

健康因子会受到抵押品价格、借款利息和治理参数变化的共同影响。即使用户没有继续借款，随着利息累积，仓位也可能逐渐接近清算线。

## 4. 清算机制

当借款人的健康因子低于规定值时，清算人可以代替借款人偿还部分债务，并以折扣价格获得对应的抵押品。

例如：

* 用户抵押的 ETH 价值下降；
* 仓位健康因子跌破 1；
* 清算人偿还用户的一部分 USDC 债务；
* 协议将部分 ETH 抵押品转给清算人；
* 清算人获得清算奖励。

清算机制的本质，是通过经济激励让外部参与者及时处理高风险仓位，从而降低协议出现坏账的概率。

但在市场剧烈波动时，如果链上拥堵、Gas 费过高或抵押品流动性不足，清算可能无法及时完成，协议仍然可能产生坏账。

## 5. 预言机的作用与风险

智能合约无法直接读取链外市场价格，因此借贷协议需要使用预言机获取资产报价。

预言机价格会直接影响：

* 用户的可借额度；
* 仓位健康因子；
* 清算是否触发；
* 清算人可以获得多少抵押品。

如果协议直接使用流动性较差的单一交易池价格，攻击者可能通过闪电贷制造短期价格波动，诱发错误清算或超额借款。

因此，成熟协议通常会采用以下保护方式：

* 使用多个数据源；
* 采用时间加权平均价格；
* 设置价格偏差限制；
* 对异常价格进行熔断；
* 为不同资产设置独立的风险参数。

## 6. 闪电贷与组合性

闪电贷允许用户在不提供抵押品的情况下借出大量资产，但必须在同一笔交易中完成借款和还款，否则整笔交易会回滚。

闪电贷可以用于：

* 不同交易平台之间的套利；
* 抵押品置换；
* 一键偿还复杂债务；
* 提高资金使用效率。

闪电贷本身只是工具。真正的风险通常来自协议的价格计算、权限控制或业务逻辑存在漏洞。攻击者可以借助闪电贷获得临时资金，放大已有漏洞造成的影响。

## 7. DeFi 借贷协议的主要风险

今天将借贷协议的风险整理为以下几类：

| 风险类型   | 具体表现               |
| :----- | :----------------- |
| 智能合约风险 | 合约代码存在漏洞，导致资产被盗或锁定 |
| 预言机风险  | 价格被操纵、更新延迟或数据源失效   |
| 清算风险   | 市场波动过快，清算不及时并产生坏账  |
| 流动性风险  | 大量用户同时提款，资金池流动性不足  |
| 抵押品风险  | 抵押资产脱锚、暴跌或缺乏交易深度   |
| 治理风险   | 管理员权限过大，关键参数被恶意修改  |
| 组合性风险  | 外部协议出现问题，风险沿调用关系传导 |

## 今日思考

DeFi 借贷协议并不是简单地将传统借贷搬到链上，而是利用智能合约、预言机和经济激励，构建一个自动运行的风险管理系统。

协议能否长期稳定运行，关键不只在于 TVL 或收益率，还要看抵押资产质量、预言机可靠性、清算效率、流动性深度以及治理权限是否合理。

高收益通常对应着额外风险。如果无法解释收益来自哪里、损失由谁承担，就不应该只根据 APY 做决策。

## 今日学习主题：MEV、交易排序与链上套利

今天深入学习了以太坊交易从提交到上链的完整过程，并重点了解了 MEV 的产生原因、常见形式以及它对普通用户和 DeFi 协议的影响。

## 1. 一笔交易是如何上链的

用户在钱包中发起交易后，首先会使用私钥对交易进行签名。签名后的交易通过 RPC 节点广播到网络，并进入节点的内存池，等待被打包。

交易大致会经历以下过程：

1. 用户构造并签名交易；
2. 钱包通过 RPC 将交易发送给节点；
3. 交易进入公开内存池；
4. 搜索者监控交易并寻找套利机会；
5. 区块构建者对交易进行排序；
6. 验证者提出区块；
7. 区块被网络确认，交易状态正式更新。

在这个过程中，交易并不一定按照提交时间排序。Gas 费、交易价值以及构建者的收益策略，都会影响最终的执行顺序。

## 2. MEV 是什么

MEV 指通过控制区块内交易的加入、排除和排序而获得的额外价值。

它并不是某一种具体攻击，而是区块链交易排序机制带来的一类经济现象。只要交易执行顺序会影响结果，就可能产生 MEV。

常见参与者包括：

* **用户**：发起兑换、借贷或清算交易；
* **搜索者**：通过程序寻找套利和清算机会；
* **区块构建者**：组合交易并构建收益更高的区块；
* **验证者**：选择区块并将其加入区块链；
* **中继器**：在构建者与验证者之间传递区块信息。

## 3. 常见的 MEV 类型

### 套利交易

同一资产在不同 DEX 中可能出现短暂价差。搜索者可以在价格较低的平台买入，再到价格较高的平台卖出。

例如：

* Uniswap 中 1 ETH 的价格为 3,000 USDC；
* Curve 中 1 ETH 的价格为 3,030 USDC；
* 搜索者在 Uniswap 买入 ETH；
* 随后在 Curve 卖出；
* 扣除 Gas 和手续费后，剩余部分就是套利利润。

这类套利有助于不同市场恢复价格一致，但也会引发激烈的交易排序竞争。

### 清算 MEV

当借贷协议中的仓位跌破清算线时，清算人可以偿还部分债务，并获得折价抵押品。

多个清算人往往会同时竞争同一个仓位。谁的交易更早被打包，谁就能获得清算奖励。因此，清算也是重要的 MEV 来源。

### 抢跑交易

搜索者在内存池中发现一笔可能影响价格的大额交易后，通过支付更高的优先费，让自己的交易先执行。

这种行为会导致原交易以更差的价格成交。

### 夹子攻击

夹子攻击通常由三笔交易组成：

1. 攻击者先于用户买入资产，推高价格；
2. 用户的大额兑换按照更差的价格执行；
3. 攻击者在用户交易后卖出资产，赚取价差。

用户设置的滑点越高，攻击者可以利用的价格空间通常越大。

## 4. 滑点与价格影响

滑点是用户预期成交价格与实际成交价格之间的差异。

价格影响则是用户自己的交易规模对资金池价格造成的改变。两者相关，但含义不同：

* **价格影响**来自交易规模与池子深度；
* **滑点**还可能受到市场变化、交易排序和 MEV 的影响。

如果用户将滑点容忍度设置得过低，交易容易失败；如果设置得过高，又可能给夹子攻击留下更大的获利空间。

因此，在进行大额兑换时，应该关注：

* 资金池深度；
* 预计价格影响；
* 最低接收数量；
* 当前网络拥堵情况；
* 是否使用 MEV 保护 RPC；
* 是否可以拆分订单或使用限价单。

## 5. PBS 与 MEV-Boost

以太坊权益证明机制中，区块提出者与区块构建者可以进行职责分离，这种设计被称为提议者—构建者分离。

区块构建者负责从交易中寻找最优组合，并向验证者报价。验证者通常选择报价最高的区块进行提议。

MEV-Boost 在协议外实现了类似流程：

1. 构建者组合交易并生成区块；
2. 构建者通过中继器提交报价；
3. 验证者选择收益最高的区块；
4. 区块内容被公开并提交到网络。

这种机制提高了区块构建市场的专业化程度，但也带来了构建者集中、中继器依赖和交易审查等问题。

## 6. MEV 的正面与负面影响

MEV 并不完全等于恶意攻击。

它的正面作用包括：

* 缩小不同交易市场之间的价差；
* 及时清算高风险仓位；
* 帮助 DeFi 协议维持偿付能力。

它的负面影响包括：

* 普通用户成交价格变差；
* 搜索者之间产生 Gas 竞价；
* 交易失败率和网络成本上升；
* 区块构建权可能逐渐集中；
* 验证者可能为了重组区块而争夺高额 MEV。

因此，MEV 的核心问题并不是“能否彻底消除”，而是如何减少恶意价值提取，并让交易排序过程更加公平和透明。

## 7. 普通用户如何降低 MEV 风险

可以采用以下方式减少潜在损失：

* 不要随意设置过高的滑点；
* 大额交易前检查资金池深度；
* 尽量使用聚合器比较不同交易路径；
* 使用支持 MEV 保护的 RPC 或私有交易通道；
* 避免在流动性较差的池子中进行大额兑换；
* 检查钱包显示的最低接收数量；
* 将大额订单拆分，或使用限价单和 TWAP 策略。

## 今日收获

今天认识到，链上交易并不是简单地按照提交顺序执行。交易进入内存池后，不同参与者会围绕排序权展开竞争，而这种排序会直接影响用户成交价格、协议清算效率和验证者收益。

研究 DeFi 项目时，除了关注合约功能和代币模型，还需要分析交易在什么环境下执行，以及价值最终被哪个参与者获取。

## 下一步学习计划

下一步准备选择一笔真实的 DEX 交易，通过区块浏览器分析：

1. 用户实际支付的 Gas；
2. 交易调用的合约和函数；
3. 代币在不同地址之间的流向；
4. 兑换前后的资金池状态；
5. 是否存在抢跑、套利或夹子交易；
6. 搜索者和区块构建者获得了多少收益。
