# 2026-07-29

📌 今日目标

Day 2 已经稳住了任务1（链上信息检索）的闭环。今天的目标是扩展 Alpha Agent 的能力边界，让它从只能做“查询分析”，升级为能同时完成“查询 + 执行 + 推理”三项综合 Benchmark。

具体任务：

1. 部署 VoteRegistry.sol 极简测试合约，作为任务2的链上交互目标
2. 为 Alpha Agent 实现任务2（链上执行）：自然语言 → 构造交易 → 发送上链
3. 为 Alpha Agent 实现任务3（链上数据推理）：数值查询 + 与标准答案比对（允许 ±5% 误差）
4. 升级评测引擎，将三项任务结果按 0.4×任务1 + 0.3×任务2 + 0.3×任务3 合并为综合评分
5. 修改链上写入逻辑：从写“单项分数”改为写“综合分数 + 完整报告哈希（Keccak256）”

✅ 完成情况

1. 任务2合约部署（链上执行）

· 编写并部署 VoteRegistry.sol 到 Monad 测试网
· 合约极简设计：仅包含 function vote(uint256 taskId) external 和对应的 Voted 事件
· 部署后记录合约地址，作为任务2的固定交互对象

1. Alpha Agent 任务2 实现（链上执行）

· 输入：自然语言指令（如 “给这次评测投票”）
· 处理流：Agent 理解意图 → 调用链上交易工具 → 构造 vote() 调用 → 发送交易 → 等待确认
· 判分逻辑：二元判定——在区块链浏览器/事件日志中查询是否存在 Voted 事件且参数正确，成功即满分，失败即零分

1. Alpha Agent 任务3 实现（链上数据推理）

· 输入：数值问题（如 “该地址最近一次交易 gas 费是多少”）
· 处理流：Agent 调用 RPC 工具获取链上原始数据 → 提取数值答案
· 判分逻辑：与 backend/data/ground\_truth.json 中预存的标准答案比对，相对误差 ≤ 5% 判定为正确

1. 综合评分与链上存证升级

· 后端评测引擎计算三项得分后，按权重公式自动合并
· 将 { agentId, finalScore, taskBreakdown } 序列化为 JSON 报告
· 计算报告内容的 keccak256 哈希值
· 调用 ReputationRegistry 合约，将 agentId、finalScore、reportHash 写入链上（至此，链上数据从“单一任务分”升级为“综合信誉分”）

🔧 遇到的问题与解决

问题 解决方案
Agent 执行任务2时，有时只生成交易参数但不主动调用发送工具 在工具描述中强制约束：“必须调用 sendTransaction 工具完成上链，仅构造参数视为未完成任务”
任务3获取的 Gas 数值（Hex 格式）与标准答案（Decimal）比较时类型混乱 在判分前增加统一的数据归一化处理层，全部转为 Decimal 字符串再计算误差
三项任务串行执行总耗时过长 任务1和任务3的链上查询改为异步并发执行，任务2因其状态依赖性保持串行

📚 今日收获

· 理解了“读写分离”的 Agent 设计：任务1/3是“只读查询”，任务2是“写操作”，同一套 Prompt 框架下需要清晰划分工具权限，防止 Agent 混淆
· 权重公式的工程落地：以前只是文档里的数学公式，今天真正把 0.4/0.3/0.3 写进了代码，并处理了浮点数精度问题
· 哈希存证的实操价值：链上只存哈希，详细数据存后端——这样既节省 Gas，又保留了完整的审计线索（Demo 时点开前端详情页能看到各项明细，点开浏览器能看到哈希对应关系）

# 2026-07-30

ay 3 已经为 Alpha Agent 补齐了任务 2（链上执行）和任务 3（数据推理）的代码实现。今天**不加新功能、不引入新 Agent**，而是对 Alpha Agent 的三项全流程任务做严格的端到端联调与加固，确保评测链路的**稳定性**和**可复现性**，为 Day 5-6 的多 Agent 对比打下可靠基础。

具体任务：

1. 完整跑通 Alpha Agent 三项任务的全流程（输入 → 推理 → 判分 → 综合评分 → 哈希计算 → 链上写入）
2. 处理任务 2 和任务 3 的边缘情况（无历史交易、RPC 限流、Gas 估算失败等）
3. 优化任务 1 和任务 3 的并发查询策略，防止 Monad 测试网 RPC 被限流
4. 验证 JSON 报告与 Keccak256 哈希的确定性（相同输入必须产出相同哈希）

### **✅ 完成情况**

**1. 端到端全流程回归测试**

* 使用 3 个固定测试地址，分别运行 Alpha Agent 完整评测（任务1+2+3）
* 验证点 1：三项任务均能正常返回得分（0\~100 的数值）
* 验证点 2：综合评分按 `0.4×任务1 + 0.3×任务2 + 0.3×任务3` 正确计算
* 验证点 3：`{agentId, finalScore, taskBreakdown}` JSON 报告生成完整，`keccak256` 哈希值与合约内存储的 `reportHash` 一致

**2. 任务 2（链上执行）边缘情况加固**

| **边缘场景**               | **处理方式**                                               |
| :--------------------- | :----------------------------------------------------- |
| 重复投票（同一 `taskId` 调用两次） | 合约层面幂等处理（已投票则直接返回成功，不重复记录事件），Agent 层面捕获合约回退并给出友好提示     |
| 非ce（Nonce）冲突导致交易卡住     | 改用 `eth_sendTransaction` 的简单重试机制（nonce 自动由节点管理，避免手动维护） |
| Gas 估算失败（合约执行异常）       | 捕获 `gas estimation failed` 错误，返回明确失败状态，不将交易广播出去        |

**3. 任务 1 和任务 3 的 RPC 并发优化**

* 原先两项任务各自独立查询 RPC，串行执行耗时约 6\~8 秒
* 改为 **异步并发查询**（使用 `asyncio.gather`），总耗时压缩至 3\~4 秒
* 增加 **RPC 请求间隔控制**（每次请求间隔 100ms），避免触发测试网速率限制（`rate limit` 报错明显减少）

**4. 哈希确定性验证**

* 多次运行同一地址的评测，生成的 JSON 报告字段顺序固定（使用 `sort_keys=True` 序列化）
* 三次运行输出的 `reportHash` 完全一致，确保链上存证的**可复现性**和**可验证性**——同一次评测结果不会被误判为两次不同结果

# 2026-08-01

我完成了项目从“单点验证”到“平台雏形”的关键跃升。

横向扩展层面，我在 Alpha 基础上新增了 Beta（速度优先）和 Gamma（成本优先）两个 Agent，三者共用同一套工具链和评测逻辑，仅通过 System Prompt 区分策略。对比验证结果显示：Alpha 综合评分最高（94+），但耗时最长；Beta 速度提升约 50%，评分略有下降；Gamma 调用次数最少（仅为 Alpha 的 1/3），但在任务 2 因简化处理出现一次失败。三者评分呈现 Alpha > Beta > Gamma 的稳定排序，且同一 Agent 多次评测标准差不超过 2.5 分——这证明我设计的 Benchmark 能够客观、可重复地识别不同 Agent 的能力差异，而不是为某个特定 Agent 定制的“花架子”。

纵向深化层面，我将零散的终端脚本整合为标准化的后端服务，实现了四个核心 API（注册、评测执行、排行榜、历史查询），并引入 SQLite 数据库持久化完整评测报告。关键的“链下报告 + 链上哈希”机制已闭环：评测生成的 JSON 报告计算 keccak256 哈希后写入 ReputationRegistry 合约，前端展示时后端会重新校验哈希一致性——这构成了防篡改的可信证据链。此外，我抽空完成了 Task 4 的高频交互简化测试（连续 10 次链上写入，成功率 100%），为 Demo 储备了技术深度展示。
