# 2026-07-29

## 今天的学习总结

 

今天我对这项 **Polymarket 流动性与执行质量研究** 的理解，已经从“会调用 API、会画图”，进一步提升到了“理解数据为什么可能不可信，以及如何设计一个能够经受审计的研究”。

首先，我理解了 Polymarket 页面上的展示价格不一定是用户真正能够成交的价格。页面通常展示买卖中间价，价差较大时可能展示最新成交价；但用户立即买入需要看 `best ask`，立即卖出需要看 `best bid`。当订单金额较大时，第一档卖单可能不够，还会继续吃掉更高价格的订单簿档位，因此平均模拟成交价会高于 `best ask`。

我也学会了如何根据订单簿模拟固定金额的买入：从最低 ask 开始，逐档计算价格乘以数量，预算足够就买完整档，预算不足就只买部分；如果订单簿全部用完后还有剩余预算，就说明可见深度不足，订单无法完整成交。此时必须同时报告已成交金额、未成交金额、买到的股数、部分成交均价、成交比例和 `full_fill=false`，不能只拿已成交部分的均价与完整成交订单直接比较。

在指标方面，我现在能够区分：

* `execution gap`：模拟执行均价与页面展示价格的差异；
* `book-walking cost`：模拟执行均价与初始 best ask 的差异；
* `realized slippage`：真实下单后的成交均价与下单时基准价格的差异。

因为目前研究只是根据静态可见订单簿进行模拟，所以不能把结果叫作实际成交价或真实滑点，只能称为 **visible-book execution estimate**。

今天另一个重要收获是理解了“共同样本”。比较 10、100、500 USDC 时，不能分别使用不同数量的快照，否则大额订单组可能只剩下本来流动性就更好的市场，制造出虚假的规模效应。主规模比较应该使用同一批能够完成所有规模计算的快照。但共同样本也会偏向深订单簿，因此还必须在全部有效样本上报告每个规模的完整成交率，以及共同样本占全部样本的比例。

我还理解了几个非常重要的数据质量原则：

> **未知不等于零。**

手续费缺失不能被当成手续费为零；订单簿字段缺失不能被当成真实零深度；没有成交不能把平均价格写成零。`None` 表示数据未知，`0` 表示已经明确确认数值为零，这两者会导致完全不同的研究结论。

此外，我理解了 stale 数据、重复订单簿档位和时间前视问题。陈旧快照代表数据太久没有被可靠确认，不能进入主分析；重复档位可能夸大深度，在官方语义未确认前不能擅自相加；请求发出时间和响应接收时间必须分别保存，否则可能把交易后收到的订单簿错误地当成交易前信息。

在代码和测试方面，我知道了每修复一个错误，都应该增加一个回归测试。例如：

* 费用为 `None` 时，含费价格也必须为 `None`；
* 缺少 bids 字段时，深度应为未知而不是零；
* 出现重复价格档位时，程序必须报错而不是静默相加。

回归测试的目的，是防止以后修改代码时，同样的错误再次出现。

在结果表达方面，我理解了平均数容易被少数极端值拉高，因此订单簿研究通常需要同时报告中位数、P25、P75、P90、样本量和完整成交率。`bps` 是基点，100 bps 等于 1%。同样 0.01 USDC 的绝对价差，在价格为 0.50 时是 2%，在价格为 0.05 时却是 20%，所以跨不同价格市场比较时，不能只看绝对差，也需要看百分比或 bps；但价格接近零时，相对指标又会非常敏感，因此最好两种都报告。

最后，我对 Codex 在项目中的角色也有了更清晰的认识。Codex可以帮助实现代码、测试和文档，但研究问题、指标定义、数据质量规则、反例设计、结果是否可信以及能否发表，必须由我自己判断。这个项目真正的亮点并不是“AI帮我生成了一篇文章”，而是：

> 我发现初始实现存在前视偏差、缺失值转零、重复深度和样本选择问题，并通过审计、反例和测试重新设计了可信的数据流程。

今天最大的学习心得是：

> **优秀的数据分析不是尽快得到一个漂亮结论，而是先证明数据、计算过程和比较方法值得信任，并且清楚说明结论能够证明什么、不能证明什么。**

# 今日学习心得

 

今天我对 **Polymarket 流动性监控、执行质量分析和运营故障处理** 的理解，已经从单纯认识订单簿指标，进一步进入了真实项目运行、数据审计和运营决策层面。

## 一、我进一步理解了订单簿执行成本

我现在能够区分：

* `best bid`：买方愿意支付的最高价格；
* `best ask`：卖方愿意接受的最低价格；
* `top of book`：订单簿最前面的最佳买卖报价，以及对应数量；
* `spread`：best ask与best bid之间的距离；
* `depth`：不同价格档位上能够成交的数量；
* `book-walking cost`：大额订单吃完第一档后，继续进入更贵档位产生的额外成本。

当10 USDC订单的执行成本基本稳定，而500 USDC订单明显恶化，同时spread基本不变时，更可能是：

> 最优卖价仍然存在，但该价格能提供的数量减少，大额订单不得不继续吃更贵的卖盘档位。

因此，这是 **ask-side depth下降**，而不是spread扩大。

我也纠正了两个容易混淆的术语：

> `best ask`是最低卖价，不是最低买价。

> `book-walking cost`是吃多档产生的成本；`crossed book`则是best bid高于best ask的异常订单簿状态。

***

## 二、我理解了不同规模订单为什么反映不同问题

小额订单通常只需要最前面的一档卖盘，因此更容易受到spread和best ask的影响。

大额订单则会消耗多个价格档位，因此对订单簿深度更敏感。

所以：

```
```

```
小额和大额同时恶化
→ 更可能是spread扩大，或者整体报价发生变化
```

```
```

```
小额基本稳定，大额明显恶化
→ 更可能是订单簿深度下降
```

但这种判断必须建立在数据质量正常的前提下，不能看到一个指标变化就直接解释市场。

***

## 三、我学会了判断异常影响范围

异常不能只笼统地说成“市场问题”，还需要判断它属于哪个层级：

*  只有一个或少数市场异常：单市场问题； 
*  同一类别的大部分市场异常：类别级问题； 
*  多个不同类别同时异常：可能是平台范围问题； 
*  大量市场同时异常并伴随延迟、stale或missing上升：优先检查数据基础设施。 

例如：

```
```

```
加密短周期市场14/15异常
政治市场只有3/10异常
```

更准确的结论是：

> 异常主要集中在加密货币短周期市场，属于类别级异常，而不是整个平台普遍恶化。

我也认识到，类别集中可能与市场波动、做市风险调整或流动性撤出有关，但这些都只能作为待验证解释，不能直接当作已经确认的根因。

***

## 四、我对REST快照的局限有了更清楚的认识

我的采集器每180秒，也就是每3分钟采集一次订单簿。

这类似于每3分钟拍一张照片，而不是连续录像。

例如系统只能看到：

```
```

```
12:00的订单簿
12:03的订单簿
```

但无法完整看到中间发生的：

*  新增挂单； 
*  撤单； 
*  成交； 
*  spread瞬间扩大后恢复； 
*  深度突然消失后再次出现。 

因此，REST快照可以支持方向性判断，但无法还原完整的事件路径，也很难证明严格因果关系。

所以运营报告中可以写：

> 当前证据更符合卖盘深度下降。

但不能直接写：

> 某个做市商撤单导致了深度下降。

当证据一致但数据是离散快照时，使用 `Moderate confidence`，也就是中等信心，是比较合理的。

***

## 五、我理解了动态基线、P90和异常持续性

我复习了：

```
```

```
中位数 = 典型水平
P90 = 大约90%的历史观察值不超过该位置
```

例如某Token过去24小时：

```
```

```
500 USDC execution gap中位数 = 1.5%
P90 = 4.0%
当前 = 6.0%
```

这意味着当前值高于过去约90%的观察值，属于近期比较极端的状态。

但单次超过P90不一定需要立即报警，因为正常情况下本来就有约10%的值高于P90。

因此更合理的告警条件需要结合：

```
```

```
数据质量正常
+
高于自身动态历史基线
+
连续多个采集周期
+
影响一定数量的市场
```

这比为所有市场设置统一的“超过5%就报警”更加合理，因为不同市场的正常流动性水平不同。

***

## 六、我完成了一次真实Pilot故障的审计

本次Pilot的状态是：

> **INCOMPLETE — CONTROLLED ABORT**

已知结果：

```
```

```
计划周期：121
完成周期：89
尝试周期：90
第90周期：CLOB /books返回HTTP 502
中止后未尝试周期：31
```

共保存：

```
```

```
89 × 50 = 4,450个Token订单簿快照
```

第90周期没有生成任何快照，也没有：

*  保存50个空订单簿； 
*  把缺失写成零深度； 
*  复制上一周期数据； 
*  后续回填； 
*  延长运行时间； 
*  偷偷启动第二次Pilot。 

我理解了：

> 502表示批量 `/books` 请求没有得到有效的订单簿响应，不代表50个Token分别返回了空订单簿。

因此：

```
```

```
HTTP 502 ≠ 空订单簿
HTTP 502 ≠ 零深度
HTTP 502 = 本次批量请求结果未知
```

这个Pilot虽然没有完成完整6小时，但它验证了采集器的完整性保护机制。

## 七、我学会了区分数据诚信和运行韧性

这次Pilot说明：

> 系统的数据诚信较强，但运行韧性不足。

数据诚信表现为：

*  4,450/4,450个完整周期预期快照全部存在； 
*  失败周期没有伪造数据； 
*  受保护文件哈希全部通过； 
*  缺失、重复档位、crossed book和无效数值均被正确检查。 

运行韧性不足表现为：

> 一次瞬时502就导致后续31个周期完全没有执行。

因此审计结果给出了：

> **CONDITIONAL GO**

意思不是允许重启本次运行，而是：

> 在满足指定条件后，可以申请批准一次新的、独立的Pilot。

## 八、我完成了离线韧性修复

新的请求级重试策略是：

```
```

```
最多3次总尝试
backoff：1秒、2秒
严格总重试窗口：95秒
```

只重试：

*  HTTP 429； 
*  HTTP 500、502、503、504； 
*  连接超时； 
*  瞬态连接错误。 

不重试：

*  HTTP 400、401、403、404； 
*  schema验证失败； 
*  无效数值； 
*  配置、哈希、写入和manifest完整性错误。 

所有请求尝试都会保存：

*  attempt编号； 
*  HTTP状态； 
*  请求开始时间； 
*  响应接收时间； 
*  延迟； 
*  backoff时间； 
*  原始响应。 

重试耗尽以后：

*  该周期标记为失败； 
*  不生成Token快照； 
*  不复制上一周期； 
*  不回填； 
*  不延长固定窗口。 

运行级失败预算为：

```
```

```
连续2个失败周期
或
累计3个失败周期
→ 受控中止
```

完整测试53/53通过，但标准覆盖率复核、新配置双哈希预检和新的明确批准仍未完成，因此当前仍然是CONDITIONAL GO。

***

## 九、我理解了为什么95秒值得特别检查

采样间隔是180秒，而一次请求的完整重试过程最多可能持续95秒。

这意味着：

```
```

```
180秒 - 95秒 = 85秒
```

最坏情况下，留给其他请求、校验、文件写入和下一周期准备的时间只有85秒。

即使重试最终成功，也必须区分：

```
```

```
原计划采集时刻
请求开始时刻
最终响应接收时刻
```

一张12:00计划采集、12:01:35才收到的订单簿，不能假装代表12:00时刻的市场。

还必须确认：

*  迟到数据是否仍符合分析条件； 
*  Gamma和CLOB是否时间对齐； 
*  下一周期是否仍锚定12:03； 
*  是否产生周期重叠； 
*  后续周期是否不断漂移； 
*  固定结束时间是否被延长。 

我认识到：

> 请求最终成功，不代表这个快照一定适合进入分析。

## 十、我学会了怎样阅读数据质量漏斗

审计结果显示：

```
```

```
双边订单簿：3,738/4,450
单边订单簿：712/4,450
stale快照：48/4,450

712个单边订单簿无法计算midpoint、spread和half-spread，因此不能进入以midpoint为基准的主execution-gap分析。

*  市场流动性不足； 
*  买卖严重不平衡； 
*  某一侧完全没有挂单； 
*  临近结算等特殊市场状态。 

因此研究应该分别保留：

### 主执行质量数据集

用于计算：

*  midpoint； 
*  spread； 
*  execution gap； 
*  half-spread； 
*  book-walking cost。 

### 市场可用性数据集

用于报告：

*  双边率； 
*  单边率； 
*  空簿率； 
*  买侧或卖侧是否能够立即执行。 

我理解了一个很重要的原则：

> 不符合某项分析条件，不代表该观察对市场质量没有意义。

```

确认数据是否可信

# 2026-08-01

## 今天的核心主题

 

今天学的是：

> **如何正确描述 execution gap 的分布，以及如何避免用一个平均值误导读者。**

重点不是多算几个统计量，而是区分：

* 典型体验；
* 尾部风险；
* 可成交覆盖率；
* 异常与正常波动。

***

## 1. Mean、Median、P90、P95分别说明什么

### Mean：平均值

把所有execution gap相加后除以样本数。

它容易被少量极端值拉高。例如大部分样本在1%左右，但少数样本达到10%甚至25%，平均值可能变成2%或3%。

因此，mean不一定代表普通用户通常遇到的情况。

### Median：中位数

排序后位于中间的值。

例如：

```
```

```
Median = 0.9%
```

表示大约一半样本不超过0.9%，另一半不低于0.9%。

它更适合描述**典型情况**。

### P90

例如：

```
```

```
P90 = 4.8%
```

表示大约90%的样本不超过4.8%，最差约10%的样本高于4.8%。

它不是说90%的样本等于4.8%。

### P95

例如：

```
```

```
P95 = 9.6%
```

表示大约95%的样本不超过9.6%，最差约5%的样本更高。

它主要帮助描述更极端的**尾部风险**。

***

## 2. 为什么不能只报告平均值

假设结果是：

```
```

```
Mean = 2.3%
Median = 0.9%
P90 = 4.8%
P95 = 9.6%
```

正确解释是：

> 大多数普通样本的execution gap低于平均值，但分布存在少量非常高的极端值，因此均值被向上拉高。

所以一份可信的结果至少应同时报告：

```
```

```
N
Mean
Median
P75
P90
P95
Full-fill rate
```

典型情况看median，尾部风险看P90和P95。

***

## 3. 分位数结果仍然可能存在选择偏差

假设500 USDC订单：

```
```

```
Eligible snapshots = 2,000
Full-fill snapshots = 360
Full-fill rate = 18%
Median gap = 0.9%
```

这个0.9%只来自能够完整成交的360个快照。

不能说：

> 500 USDC订单通常只需要承担0.9%的成本。

更准确的是：

> 在能够完整支持500 USDC订单的18%合格快照中，execution gap中位数为0.9%。

另外82%的快照无法完整成交，不能从结果中消失。

因此：

> **低conditional median不等于平台整体的大额执行质量很好。**

***

## 4. 一次超过P90不代表发生事故

假设当前execution gap超过过去24小时的P90，不能马上宣布流动性事故。

原因是：

> 按照P90的定义，历史上本来就大约有10%的有效观测会高于它。

需要继续检查：

1.  数据是否fresh、two-sided、non-crossed； 
2.  是否连续多个周期超过阈值； 
3.  是否同时影响多个订单规模； 
4.  full-fill rate是否下降； 
5.  spread是否扩大； 
6.  visible depth是否下降； 
7.  是否影响多个Token或市场。 

更合理的告警逻辑是：

```
```

```
数据有效
+ 超过Token自身动态基线
+ 连续多个快照
+ 影响达到一定范围
```

而不是：

```
```

```
一次超过P90
= 立即发生事故
```

***

## 5. 为什么使用动态阈值，而不是统一5%

不同Token的正常流动性状态差异很大。

例如：

| 指标    | Token A | Token B |
| :---- | :------ | :------ |
| 历史P90 | 1.2%    | 8.0%    |
| 当前Gap | 2.0%    | 5.0%    |

虽然Token B的绝对gap更高，但：

*  Token A已经超过自己的历史P90； 
*  Token B仍处于自己的正常范围内。 

所以Token A可能更值得关注。

正确思路是：

> 每个Token使用自己的rolling median、P90或P95作为动态基线，并结合订单规模、市场波动和数据质量判断。

***

## 6. Absolute gap、relative gap和bps不能混淆

假设：

```
```

```
Displayed price = 0.50
Execution price = 0.51
```

### Absolute gap

```
```

```
0.51 - 0.50 = 0.01
```

即1美分。

### Relative gap

```
```

```
0.01 / 0.50 = 2%
```

### Bps

```
```

```
2% = 200 bps
```

所以正确表达是：

> 绝对gap为0.01，相对gap为2%，即200 bps。

注意：

```
```

```
1 bp = 0.01%
100 bps = 1%
```

***

## 7. 为什么低价格Token的相对gap容易失真

假设：

```
```

```
Displayed price = 0.02
Execution price = 0.03
```

绝对gap仍然只有：

```
```

```
0.01
```

但相对gap是：

```
```

```
0.01 / 0.02 = 50%
```

即5,000 bps。

这不代表绝对价格变化特别大，而是因为分母太小。

所以低价格Token不能只看relative gap或bps，还需要同时报告：

*  absolute gap； 
*  relative gap； 
*  display price； 
*  price bucket。 

***

## 8. 为什么需要按display price分桶

可以将Token按展示价格划分为：

```
```

```
0.00–0.10
0.10–0.30
0.30–0.70
0.70–0.90
0.90–1.00
```

然后在相似价格区间内比较execution gap。

这样可以避免：

> 低价格Token因为分母很小，产生特别夸张的relative gap，从而扭曲总体结果。

# 2026-08-02

## 今天的核心主题

今天学的是：

> **如何在SQL分析中避免因为表粒度、重复键和错误JOIN，把同一条数据重复计算。**

这类错误很危险，因为SQL可能正常运行、图表也能生成，但最终指标是错的。

***

## 1. 什么是粒度

粒度就是：

> 一张表中的一行代表什么。

例如：

### `token_snapshots`

一行代表：

> 一个Token在一个采样时点的订单簿状态。

粒度：

```
一个snapshot × 一个token
```

可能的唯一键：

```
snapshot_id + token_id
```

### `execution_estimates`

一行代表：

> 一个Token在一个快照中，对某个订单规模的执行模拟。

粒度：

```
一个snapshot × 一个token × 一个order size
```

可能的唯一键：

```
snapshot_id + token_id + order_size_usdc
```

### `quality_issues`

一行代表：

> 一个Token快照中发现的一种质量问题。

粒度：

```
一个snapshot × 一个token × 一个issue type
```

最重要的记忆：

> **粒度就是“一行代表什么”。**

***

## 2. 为什么JOIN会复制数据

假设一个execution记录对应三个quality issues：

```
stale
crossed
missing
```

直接JOIN后：

```
1条execution × 3条issues = 3行
```

原来的execution gap可能被重复三次。

例如真实只有：

```
execution_gap = 0.08
```

JOIN后错误求和可能变成：

```
0.08 + 0.08 + 0.08 = 0.24
```

所以JOIN之前必须判断：

* 左表粒度；
* 右表粒度；
* JOIN键；
* 是一对一、一对多，还是多对多。

***

## 3. 一对一、一对多和多对多

### 一对一

左表一行最多匹配右表一行。

```
1 × 1 = 1行
```

### 一对多

左表一行匹配右表多行。

```
1 × 3 = 3行
```

左表字段会被复制。

### 多对多

例如同一快照有：

* 3个订单规模；
* 2个质量问题。

JOIN后：

```
3 × 2 = 6行
```

两边的数据都会被重复。

***

## 4. 为什么LEFT JOIN也可能让行数增加

常见错误理解：

> LEFT JOIN保留左表，所以结果行数一定等于左表。

不对。

LEFT JOIN只保证：

> 左表每行至少保留一次。

如果右表有3条匹配记录，左表一行会被复制成3行。

所以只有当右表JOIN键唯一时，LEFT JOIN才可能保持左表行数不变。

***

## 5. 为什么不能直接用`DISTINCT`解决重复

`DISTINCT`只能删除完全相同的结果行。

如果两条记录的时间或execution gap不同：

| snapshot | size | gap  |
| :------- | :--- | :--- |
| S1       | 100  | 0.02 |
| S1       | 100  | 0.05 |

它们不是完全重复，`DISTINCT *`不会删除。

更重要的是，即使强行只保留一行，你仍然需要回答：

> 为什么选这一行，而不是另一行？

正确去重规则应该来自业务规范，例如：

* 使用第一次成功结果；
* 使用最后一次有效结果；
* 保留固定run版本；
* 发现重复后直接报错；
* 全部保留并标记duplicate。

不能为了让数字正常而随便去重。
